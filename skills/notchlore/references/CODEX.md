# Codex execution rules

Use these shared executor rules with a concrete assignment in either execution mode. ChatGPT maintains accepted intent and planning documents; establish actual implementation and evidence in the application workspace. Dot may coordinate work through an available, authorized connection. A business goal supplied directly to Codex can enter through [CONVERSATION.md](CONVERSATION.md) first; ChatGPT is not a mandatory prerequisite for useful work. These rules alone supply neither a project goal nor deployment authority.

## Enter at the actual stage

Identify the application workspace before changing files. The prompt archive is not the application repository. Inspect applicable instructions, actual source, relevant records, local changes, and available verification tools. Preserve unrelated work, existing skills, and newer decisions. Never assume a clean checkout or create a fictional revision or session reference.

Start from what exists: an empty folder, documents only, code only, partial records, an implementation in progress, returned results, or a live system. Reconstruct the missing context relevant to this task. Do not restart completed discovery or require every project to pass through the same phases. An audit-only request remains read-only.

Compare the actual checkout with the supplied snapshot. Source establishes implementation; accepted documents establish intent; neither automatically proves the other. Reconcile routine differences and update affected assumptions. Isolate a consequential conflict rather than resetting newer work or following stale edits blindly. When an incoming folder contains replacement documents, compare them with their current owners before applying them. Treat proposed output paths as proposed, and use the exact supplied task location rather than guessing a fixed inbox path. Check for an existing writer and uncertain external effects before starting or retrying work.

## Establish the execution contract

Extract or reconstruct a compact brief containing:

- **Destination:** audience, intended value, accepted operating boundaries, and constraints to preserve.
- **Now:** this checkpoint, required outcomes, exclusions, acceptance, and permitted actions.
- **Next/later:** relevant prerequisites, deferred goals, and activation conditions; future work is not current authority.
- **Baseline and references:** observed source state, exact available documents, owning modules, affected callers, contracts, and environment.
- **Limits and recovery:** actual time, cost, resource, or attempt limits; protected data; the needed baseline, backup, and restore path.

Reuse the current project and task records. Proposed output paths are not existing prerequisites. If an empty project is authorized, inspect the selected folder and create the required records as part of the task. Do not overwrite applicable instructions or introduce competing canonical documents.

Read [METHOD.md](METHOD.md), [CONTEXT.md](CONTEXT.md), [SYSTEM.md](SYSTEM.md), and [HANDOFF.md](HANDOFF.md) as the task requires. They are included with the installed skill; an imported assignment may provide them separately. These links do not make other ChatGPT attachments visible in the workspace. The assignment must carry the essential scope and accessible references; request only task-critical missing context. Do not assume `$notchlore` is installed or install software merely to obtain missing context.

Before implementation, declare the exact release envelope: target maturity, active scope/plane, candidate/environment and applicable mandatory gates. Do not weaken it after a failed or unavailable check. Ensure active goals map to coherent design, owning references, and meaningful checks. Apply the documentation Aperture and mandatory design gates in METHOD.md; resolve thin descriptions through CONVERSATION.md instead of handing the customer an architecture questionnaire. If an unknown requires research or an experiment, execute the authorized bounded investigation and retain the broader goal as unproved. Resolve routine technical choices yourself. Ask one consequential product or business question only when evidence and existing authority cannot settle it.

## Execute and criticize the result

Choose the smallest justified route: extend the current owner, narrowly refactor a demonstrated blocker, or isolate an experiment with an exit condition. Use suitable existing tools and patterns. Work through the unfinished Try, Adjust, and Polish radii; they do not change the release promise.

Continue the authorized loop without asking approval for each correction:

1. Select a material unmet goal or failed assumption and a useful action.
2. Make a coherent change or gather the evidence needed to decide.
3. Check relevant outcomes across D01–D12 and their linked goal/evidence dependencies.
4. Criticize the candidate against the goals, source, and documents. Name the mismatch, consequence, smallest correction, and closure check.
5. Correct the responsible owner, update affected records, and recheck the integrated result.

Keep one owner per business rule and durable fact. Migrate affected consumers together. Unify matching semantics and formats without erasing meaningful distinctions or trust-boundary checks. Complete the relevant success, rejection, duplication, interruption, retry, cancellation, and recovery paths. Preserve compatibility; avoid speculative layers, configuration sprawl, hardcoded environment policy, and fake-success fallbacks.

For substantial changes, inspect actual input cardinality and hot paths: time/space growth, repeated scans, N+1 queries, indexing, full-history work, fanout, allocations, retry/queue costs and observer interference. Establish a representative baseline and compare candidate workload/query counts, latency/resources and required bounds. Linear work is legitimate when every item must be processed. Test pagination/continuation to completion; do not drop accepted work to appear fast. Record fixture, conditions, denominator/window and limitations; no invented SLA or performance numbers.

After meaningful corrections run the implementation-plane assessment for the exact candidate/environment. All four independent types must be assessed per applicable dimension; derive each score from retained findings, not model-entered numbers. An UNKNOWN or stale dimension, failed dimension, unpassed mandatory gate or authority blocker prevents acceptance even when other scores are ten. Keep a bounded UNC separate from an unassessed candidate. A required missing verifier is DEF; an existing unrun verifier is UNC; both leave the mandatory proof unpassed. Use the shipped structural checker where available and review semantic sufficiency separately.

Use existing checks and focused evidence for changed invariants. Discover actual commands from the project and installed tooling. Do not invent flags, mirror implementation with pointless tests, rerun everything without cause, or weaken acceptance. A report of tests passing is not proof of an untested journey, deployment, or business outcome. Label synthetic fixtures, mocks, local integration, physical platform, live provider and operating evidence accurately. Required integrations cannot be replaced with fake-success stubs or demonstration data.

Use METHOD.md's stopping and pivot rules: at a material stall consider a different approach; after two attempts without useful information stop repeating that path. Continue independent authorized work when one part is blocked. One long business iteration may contain many internal correction passes; do not ask the user to restart each one. Stop when the current gates pass, an explicit limit or pause applies, or no useful authorized action remains. A status question does not cancel the task; an explicit pause or cancellation does.

## Coordinate without losing ownership

If Dot's connection is established, accept scoped assignments and return evidence through that route. Otherwise deliver the named report and files for manual transfer; do not claim to have notified another chat.

Delegate only useful independent work. Give every contributor the brief, authority, references, and expected output. Assign one writer per file and an integration owner. Review a stable candidate against its actual document/source baseline. Recheck changed premises after integration. Without a separate reviewer, report structured self-review honestly. Role agreement cannot replace evidence, grant new authority, or waive mandatory goals.

## Leave a usable result

Update the selected checkpoint after meaningful transitions, before a handoff or foreseeable interruption, and on completion. Record stable task ID/type/tags/status, maturity/workflow/radius/route, decisions, source/dirty state, actual run/session and writer, permissions/limits, goal coverage, complete findings, pending/unknown effects, evidence and exact next action. Distinguish checkpoints, backups, and verified baselines; source rollback does not itself reverse data changes. Follow actual backup cadence and retention where configured; do not claim a checkpoint schedules backups or keeps the agent running.

Return the changed behavior, source identity and local changes, affected files, current project/task records, relevant source or a usable diff, and verification evidence with environment. Use PASS, FAIL, BLOCKED, NOT RUN, INCONCLUSIVE, or N/A with reasons. Separate prepared, implemented, tested, deployed, and release-qualified claims. For a refactor, identify the resulting owner, migrated consumers, retired duplicate, and preserved behavior. Package the required return artifacts through HANDOFF.md, exclude secrets and unrelated data, and verify their actual contents. Keep the final chat reply short and link the actual files. If file tools are unavailable, provide complete named content without claiming it was saved or transferred.
