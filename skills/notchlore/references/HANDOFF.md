# From current knowledge to executable work

Use this contract for source snapshots, task packets, returns and recovery. The owner gives a business outcome; the engineer prepares complete context and an exact next step. Modes 2 and 3 share these records. Manual transfer is supported directly; Dot changes transport only when an authorized connection actually works. Mode 1 can finish with developed documents and review without any executor.

## 1. Establish readiness and authority

Assume the executor can see only its actual checkout and the transferred packet. It cannot read this conversation, prior chats or attachments unless explicitly supplied. Use [CONVERSATION.md](CONVERSATION.md) to develop the current project record, then [METHOD.md](METHOD.md)'s documentation plane to assess the exact scope and mandatory design gates. Do useful preparation before a consequential question. Accepted decisions and permissions persist; a ready authorized task does not need another approval to write its handoff.

A design can pass while runtime remains NOT RUN. Keep an unmet premise that is necessary for design feasibility blocked; a bounded investigation may be ready even though the broader feature is not. An audit-only task remains read-only. An implementation task authorizes ordinary in-scope design clarification, coding, verification, repair and record updates; it does not imply publishing, production changes, new paid services, broad refactoring or future roadmap features.

If there is no repository, prepare a self-contained first task with all necessary records included. It must identify and inspect the selected target directory before creating the approved project. Existing contents stay protected. A required input is an actual included or verified existing file; a planned output is never a prerequisite that the recipient is expected to find.

## 2. What appears where and when

Use existing project paths and document owners. The engineer fills exact paths from the actual task; defaults are suggestions until materialized. Uploading to ChatGPT does not place files on a VPS, and selecting a chat pack does not install the Codex skill.

| When | Where | Result and owner |
| --- | --- | --- |
| Obtain the release | Supplied matching release, or verified published revision | One maintained method, CLI/skill and three generated independent mode packs. Choose one pack; no manual merging. |
| Set up planning | Selected ChatGPT chat/project | Read START, BASE, selected adapter and needed canonical references from the supplied pack or accessible pinned revision. This provides rules, not application access. |
| Install the skill | Actual local/VPS project directory | Installer owns `.agents/skills/notchlore/` only. Preserve source, docs, AGENTS.md, other skills and edited content. Global installation is optional where supported. No app, daemon or backup job is created. |
| Inspect an existing project | Actual workspace, then planning chat | Executor reads relevant source and prepares a scoped source/docs packet when needed. Planning assistant records current observed behavior and evidence limits. Use already adequate supplied material. |
| Develop a goal | Planning draft and actual downloadable records | Assistant evolves one complete record plus concise view, diagrams and assessment. Mark proposed/accepted state and source baseline. These files have not silently appeared in the repository. |
| Hand off | One task ZIP | Include START, task, accepted/proposed records, acceptance, references and manifest. Declare exact receiving project, fresh staging directory, reconciliation targets, return path and one short starter. |
| Receive | Fresh task-specific staging directory | Validate archive and baseline, inspect current local changes, compare proposed records, reconcile accepted content into existing owners. Staging is temporary input, not a second permanent manual. |
| Execute | Checked project worktree | Executor implements, tests, repairs, updates canonical docs and checkpoint, and records actual evidence for the candidate. |
| Return | Sanitized result ZIP, then planning chat | Include current records, actual source or usable diff, evidence and unresolved findings. Planning assistant reviews the bytes and reconciles its view. |
| Recover | Same project and durable checkpoint | Inspect source, active writer/process, permissions, pending effects and remaining gates. Use a healthy verified native resume or a fresh session with the checkpoint. |

During manual exchange, the planning draft and repository are separate revisions. The task declares its base and intended changes; applying it requires reconciliation and a recorded resulting revision. Never silently use last-write-wins. Reuse `docs/notchlore/project.md`, `iteration.md` and `report.md` only if no suitable existing owner exists. Create the report when results exist, not as fabricated proof in the incoming task.

## 3. Fill one complete cold task

A full task is a document, not a user-copied prompt. The starter is at most 200 characters including spaces and points to its actual included START/task path. Fill the following responsibilities from evidence; omit only genuinely inapplicable details with reasons.

| Responsibility | Required content |
| --- | --- |
| Identity and placement | Stable task ID/type/tags, project and root, packet revision, exact fresh staging path, canonical reconciliation targets, reading order and exact return destination. |
| Baseline | Actual commit or snapshot identity, revision/dirty state, relevant untracked files, environment, source limitations and protected work. Never invent a commit for a ZIP. |
| Intent | Audience and final business outcome; Destination/Now/Next/Later; approved present result; all preserved features, current limitations and relevant later constraints. |
| State | Target maturity and scope, current workflow state, route and Try/Adjust/Polish radius; explicit mapping for project release terminology. |
| Authority | Allowed file/resource actions, exclusions, deployment/publication boundaries, actual permissions, cost/time/usage/attempt budgets, stop conditions and escalation criteria. |
| Accepted decisions | Concrete choices, authority/date, rationale, meaningful alternatives and rejected options; distinguish proposal, inference, observation, proof and history. |
| Product | Actual actor journeys, variants, onboarding/status/errors, supported interfaces and complete visible outcomes. |
| Design owners | Domain/component responsibility, dependency direction, proper existing owner, callers, reused tools, narrow refactor or contained experiment with exit criteria. |
| Contracts and data | Required/optional/default fields, identifiers, types/units/precision, version, states/errors, ordering, bounds, transactions, source of truth, producers/consumers, migrations and projections/freshness. |
| Lifecycle | Success, invalid/unauthorized/stale input, duplicate/reorder, interruption, cancellation, retry, restart, uncertain external effects, recovery and terminal disposition. |
| Access | Actors/actions/resources, public/private/logged-in/control/partner/agent surfaces, auth, scopes/expiry/revocation, data privacy, limits and credential references only. |
| Operating shape | Actual local/VPS/external components and chosen stores/queues/workers; three work clocks and their owner, acceptance, completion, retry and freshness; gateway/domains/TLS only if needed. |
| Compatibility | Existing APIs/settings/data/formats/platforms/hardware to preserve; prerequisite lifecycle; intended support versus observed qualification. |
| Performance | Actual cardinalities/hot paths, time/space growth, N+1/scans, indexing/pagination/continuation, workload/query-count/latency/resource baseline and candidate gates, bounds and observation overhead. |
| Acceptance | Goal-to-design-to-check mapping; separate document/implementation assessments; D01–D12 coverage, complete findings, mandatory gates, exact expected state/threshold, fixture/method, candidate/environment and evidence to return. |
| Recovery | Pre-risk backup/verified baseline, consistency and restoration obligations, checkpoint cadence, timezone, retention/missed runs where scheduled, source/data/config recovery distinctions. |
| Return | Current records and summary, changed source or applicable diff with matching baseline, real check results/logs, exact candidate, deviations, limitations, current process/effects, backup/checkpoint and next action. |

For every required reference record whether it is included, verified in the recipient baseline, or genuinely external and accessible. Include remote content locally when necessary access is uncertain and permission permits. Missing required references block dispatch of dependent work; do not replace them with “as discussed.” A reference manifest proves closure only for declared references; review the task prose for undeclared dependencies too.

The complete task directs the ordinary loop: inspect → select material gap → act → verify → criticize → correct owner/callers → update records. Give the executor room for normal technical judgment while preserving goals. It should use known project commands, inspect actual tools when commands are unknown, and never invent flags, tests, runtimes or approvals.

For substantial changes require meaningful behavior characterization before risky refactor, normal/negative/recovery checks, real integrations where promised and measured performance where relevant. A synthetic fixture may prove a bounded algorithm or contract; it cannot be labeled live provider, customer, physical platform or production evidence. Apply the two-plane score/gate contract rather than a blanket PASS.

## 4. Produce, validate and stage the real packet

The release CLI supplies `notchlore packet create`, `notchlore packet check` and `notchlore packet unpack`. Installing only the skill does not install a persistent `notchlore` shell command. Use the verified release CLI or the local-tarball runner documented in its GUIDE; establish the actual executable and package path before invocation. Packet commands use Python 3's standard-library ZIP handling through Node 22 or newer. Consult that CLI's help and supplied packet schema/example for exact fields and options. The engineer constructs the spec from real files and destinations; the business owner does not author it.

If the CLI, Python or archive/file access is unavailable, deliver the complete named task/documents and actual required references through the available authorized file route, with exact placement and the missing mechanical checks labeled NOT RUN. The recipient validates and reconciles before mutation. Do not invent a globally installed command, claim automatic validation or require installing a new service merely to use the method.

The spec explicitly selects regular files, declares the source baseline and required references, and lets the helper produce a reviewable manifest with hashes and exclusions. Keep source, task, return, checkpoint and backup purposes distinct. An export is intentionally scoped; it cannot discover every semantically necessary file or certify the absence of private information. Snapshot relevant dirty/untracked work, tests, lockfiles, schemas, docs, redacted config and deployment instructions when needed. Do not infer completeness from a filename containing “full.”

Exclude .env values, live credentials/private keys/tokens/cookies, customer messages, database contents, raw private logs, caches, dependency trees and unrelated artifacts by default. Inspect the actual selected bytes and manifest before transfer. Secret scanning and .gitignore are not privacy guarantees. Redaction may remove necessary meaning; disclose material omissions and prefer synthetic fixtures or a narrower authorized inspection. Never claim a human-reviewed archive is automatically leak-free.

Create the archive at a new destination, then check its structure/reference closure and baseline against the intended checkout. Verify the final bytes, not only the original directory. Checkers reject unsafe absolute/traversal paths, symlink/special-file escapes, collisions, unbounded entries/expanded sizes, missing references and mismatched declared identity. Their structural success establishes declarations and file availability, not correctness or authorization.

Use a matching release for packet production and receipt. Packet format 1 validates the exact generated START as well as payload hashes; a template change requires a compatibility decision or format revision. Preserve a matching frozen helper/archive pair for historical evidence. Do not rewrite an old archive to suppress a refusal; regenerate from reviewed source when moving to a different format implementation.

Unpack only into a fresh task-specific staging directory. Prepare its parent explicitly before invoking `packet unpack`, and leave the final task directory absent for the helper to create exclusively. For the default existing-project placement, run `mkdir -p -- .notchlore/staging` from the verified project root, then use the exact `.notchlore/staging/<task-id>` destination named in START. For an empty baseline, use the existing parent of the project for a sibling staging directory. The helper requires the parent to exist and creates only the final task directory. It is not a live merge tool and does not overwrite application files. Inspect START, manifest, source identity and the complete task, then compare each proposed document or source change with the actual existing owner. Preserve local/newer/foreign work. A stale baseline requires reconciliation and reassessment before mutation, not ignoring the check or weakening the manifest. Changing a spec alone does not make old evidence valid.

Every delivered transfer includes:

1. The actual ZIP and exact target project/staging path.
2. A readable START with actual included paths, reconciliation destinations, expected return and short initiation prompt.
3. The complete current docs/task/evidence references and source/baseline identity.
4. Exact validation/placement steps, including parent-directory preparation, applicable to the receiving environment; mark a destination proposed if not verified.

Do not ship an example starter pointing to a nonexistent demo path. Generate its path from the actual packet and count it. If the skill is verified installed, the starter can invoke `$notchlore`; otherwise the included complete task and shared execution reference must suffice. For a matching chat pack, START.md is included. If file creation or ZIP reading is unavailable, supply the exact named files with an explicit limitation rather than claim transfer occurred.

Manual ZIP transfer is the default. A verified repository revision, existing connector or authorized SCP/SFTP/SSH/Dot route may carry the same data. Confirm recipient access and actual version; links do not install software or synchronize chats. Do not request broad credentials or install a bridge to repair a missing connection. Finish the full usable manual handoff when connected dispatch is unavailable.

## 5. Review the return and continue

A returned report is a claim until supported. Read its actual changed source/diff, current documents and evidence against the accepted task. A diff requires its matching available baseline; otherwise obtain the relevant current files. Bind each gate to candidate, environment, fixture/method and validity. Preserve PASS, FAIL, BLOCKED, NOT RUN, INCONCLUSIVE and justified N/A without converting missing proof into success.

Trace changes through owners, callers, access, formats, storage, effects and terminal outcomes. Compare promised and actual scope, preserve existing paths and deferred goals, and re-open evidence invalidated by source/config/environment changes. Review unexpected changes and uncertain effects before another run. Do not substitute a test count, agent agreement or polished report for untested business, provider, platform, security, load or recovery evidence.

If a repairable in-scope gap remains, prepare or dispatch its concrete correction without another routine approval. If evidence invalidates the design, reconcile its owning record and affected contracts/gates before continuing. Ask only the genuine consequential product/access/cost/authority question. Continue independent work when one branch is blocked. If acceptance passes, synchronize the full and short current records and stop optional polish.

Separate prepared, implemented, tested, deployed and release-qualified claims. Preserve business hypotheses such as adoption or time saved as unproven until appropriate observation exists. The user receives the actual result, material gaps and one next action; detailed findings and proof remain in the return.

## 6. Recover without reconstructing the chat

Use [CONTEXT.md](CONTEXT.md)'s durable work record. Check task/project identity, accepted decisions, current source/dirty state, active writer/process, permissions and budget, pending or unknown effects, last evidence and next action. An interrupted result channel does not establish that work stopped or a write failed. Reconcile before retry; do not start a competing writer.

Use a verified healthy native resume mechanism if available. Otherwise a fresh executor reads the complete checkpoint and actual repository. Neither restores decisions that were never recorded. Keep checkpoint, backup, verified baseline and running process separate. Preserve the prior assessments when explicit scope changes are accepted.

Prompt instructions guide an active agent; they are not a persistent controller, scheduled backup or Dot connection. Unattended continuation requires an actually supported tested supervisor with one run owner, durable acceptance, interruption/duplicate-dispatch/unknown-effect handling, limits and permission refusal. The release's manual and active-run workflow remains usable when that external capability is unavailable.
